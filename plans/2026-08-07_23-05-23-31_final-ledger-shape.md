## What was asked

The operator pasted a rendered scope ledger from a real review — three columns:
decision, item, and one line of why — and asked "can we add this?".

Read as: make that compact shape the standard **final output** ledger, instead of
dumping the eight-column working table at the reader.

## What the check found

`SKILL.md` required output item 6 says "Final scope ledger: Add / Defer / Skip / Kill,
with a benefit line on every Add". It names the thing but never says what it looks
like. So every run invents its own layout.

The eight-column Phase 5 table is a *working* table — user pain, user value, business
value, effort, risk, decision, reason. Good for thinking, poor for reading. Phase 5 is
locked, so it cannot change, and it should not: the two tables do different jobs.

## The wrinkle in the operator's own example

The third column is not a benefit line in every row.

- `ADD NOW` rows hold a benefit line.
- The `DEFER` row holds a **reopen condition** — "client #3, or one client over 150
  seats, or two prospects raise it".
- The `SKIP` row holds a **reason** — "it is cross-tenant by definition".

Calling the column "Benefit line" would be wrong for half the rows. Calling it "Why"
and saying what each decision type puts there matches what the operator actually wrote.

## The product decision (execforge)

**Mode used:** single isolated review. Documentation only, one revert undoes it.

**Gatekeeper: YES.** An output shape that is never defined gets reinvented every run,
and the reader pays for it each time.

**Scope mode:** Hold Scope. This defines the shape of something that already exists. No
new concept.

**CEO view:** the compact table is what a reader actually looks at. Three columns is the
right width for a decision record — any more and the eye stops.

**COO view:** cheap. About twenty lines, no runtime. The only risk is drift between the
working table and the final table; naming which is which prevents that.

**Scope ledger:**

| Decision | Item | Why |
| --- | --- | --- |
| `ADD NOW` | Three-column final ledger shape in Phase 5a | Defines an output that is currently reinvented every run; unlocks a decision record a reader can scan in one pass |
| `ADD NOW` | Say what the `Why` column holds per decision type | The operator's own example proves one rule does not fit all four decisions |
| `SKIP` | Changing the Phase 5 working table | Locked, and the two tables do different jobs. |
| `SKIP` | Any change outside `execforge` | Product only, same as the last change. |

**Verdict: GO.**

## Choices made

| Date | What we chose | Why |
| --- | --- | --- |
| 2026-08-07 | Column called `Why`, not `Benefit line` | The operator's own `DEFER` and `SKIP` rows hold a reopen condition and a reason, not a benefit. |
| 2026-08-07 | Put it in Phase 5a, not a new section | Phase 5a already governs what goes in these cells. One home, not two. |
| 2026-08-07 | Keep the eight-column working table | It is locked, and it is where the thinking happens. The new table is what gets read. |
